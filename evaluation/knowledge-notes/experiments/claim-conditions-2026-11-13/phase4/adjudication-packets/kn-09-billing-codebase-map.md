# Phase 4 adjudication packet: kn-09-billing-codebase-map

## Source units (id [heading path] text)
u1 [Ledgerline billing service: codebase map › About this map] This note maps the invoice path of the Ledgerline billing service as of commit `a41c9e2`.
u2 [Ledgerline billing service: codebase map › About this map] I read the code by hand; nothing here was generated by a tool.
u3 [Ledgerline billing service: codebase map › About this map] Every statement says how I know it: "the code does" means I read it in the file named, "my reading" is my own interpretation, "probably" means I suspect it but did not confirm it, and "unknown" means I looked and could not find out.
u4 [Ledgerline billing service: codebase map › About this map] Refunds, dunning and the customer portal are out of scope.
u5 [Ledgerline billing service: codebase map › Modules on the invoice path] `billing/invoices` holds the entry point, the draft type and the write to the invoice tables.
u6 [Ledgerline billing service: codebase map › Modules on the invoice path] `billing/usage` turns raw usage events into usage lines.
u7 [Ledgerline billing service: codebase map › Modules on the invoice path] `billing/pricing` turns usage lines into priced lines.
u8 [Ledgerline billing service: codebase map › Modules on the invoice path] `billing/tax` wraps the external tax provider.
u9 [Ledgerline billing service: codebase map › Modules on the invoice path] `billing/events` publishes billing events for other services to consume.
u10 [Ledgerline billing service: codebase map › Modules on the invoice path] Each module exposes its functions through its own `index.ts` file.
u11 [Ledgerline billing service: codebase map › Modules on the invoice path] The modules import each other only through those index files; I found no import that reaches into another module's internal files.
u12 [Ledgerline billing service: codebase map › Invoice generation entry point] The code defines `generateInvoice(accountId, period)` in `billing/invoices/generate.ts`, lines 12–58.
u13 [Ledgerline billing service: codebase map › Invoice generation entry point] It is the only exported function in that file.
u14 [Ledgerline billing service: codebase map › Invoice generation entry point] The admin console's "Regenerate invoice" action calls it from `billing/admin/regenerate.ts`.
u15 [Ledgerline billing service: codebase map › Invoice generation entry point] `generateInvoice` does its work in a fixed order.
u16 [Ledgerline billing service: codebase map › Invoice generation entry point] First, the code calls `collectUsage(accountId, period)` to get the usage lines for the period.
u17 [Ledgerline billing service: codebase map › Invoice generation entry point] Second, it calls `priceUsage(lines, plan)` to turn those lines into priced lines.
u18 [Ledgerline billing service: codebase map › Invoice generation entry point] Third, it calls `TaxClient.quote(draft)` to get the tax for the draft invoice.
u19 [Ledgerline billing service: codebase map › Invoice generation entry point] Finally, it writes the invoice and publishes an event, as described under "Persistence and events" below.
u20 [Ledgerline billing service: codebase map › Usage and pricing] The code in `billing/usage/collect.ts` defines `collectUsage(accountId, period)`.
u21 [Ledgerline billing service: codebase map › Usage and pricing] It reads the `usage_events` table, selecting the account's rows whose `occurred_at` falls inside the period, and groups them by meter into usage lines.
u22 [Ledgerline billing service: codebase map › Usage and pricing] Events flagged `is_test` are skipped.
u23 [Ledgerline billing service: codebase map › Usage and pricing] It does not write to any table.
u24 [Ledgerline billing service: codebase map › Usage and pricing] The code in `billing/pricing/priceUsage.ts` defines `priceUsage(lines, plan)`.
u25 [Ledgerline billing service: codebase map › Usage and pricing] It reads the `price_plans` table through a helper in the same file, `loadPlan(planId)`, and multiplies each line's quantity by the plan's unit price.
u26 [Ledgerline billing service: codebase map › Usage and pricing] Prices are held as integer cents throughout, never as floating-point amounts.
u27 [Ledgerline billing service: codebase map › Usage and pricing] `priceUsage` probably also reads the `discounts` table.
u28 [Ledgerline billing service: codebase map › Usage and pricing] The file imports a helper called `discountFor`, and the name suggests a discount lookup, but I did not find a call site and have not confirmed that it ever runs.
u29 [Ledgerline billing service: codebase map › Usage and pricing] Treat this link as unconfirmed until someone traces it.
u30 [Ledgerline billing service: codebase map › Tax] The code in `billing/tax/client.ts` defines a `TaxClient` class whose `quote(draft)` method sends the draft invoice to an external tax provider, Taxwell, over HTTPS.
u31 [Ledgerline billing service: codebase map › Tax] The request has a timeout of 8 seconds, set on line 21.
u32 [Ledgerline billing service: codebase map › Tax] The API key is read from the `TAXWELL_API_KEY` environment variable when the client is constructed.
u33 [Ledgerline billing service: codebase map › Tax] The response carries a tax amount for each line, which `generateInvoice` adds to the draft before saving it.
u34 [Ledgerline billing service: codebase map › Tax] How retries work for the tax provider is not documented.
u35 [Ledgerline billing service: codebase map › Tax] `TaxClient.quote` contains no retry code, and I could not find out whether its callers retry, whether the Taxwell client library retries on its own, or what happens to the invoice when a quote times out.
u36 [Ledgerline billing service: codebase map › Persistence and events] The code writes the finished invoice to two tables, `invoices` and `invoice_lines`, inside one database transaction in `billing/invoices/generate.ts`, lines 44–52.
u37 [Ledgerline billing service: codebase map › Persistence and events] If either insert fails, the transaction rolls back and neither row is kept.
u38 [Ledgerline billing service: codebase map › Persistence and events] The `invoices` row is written with the status `finalized`; I found no code path that writes any other status.
u39 [Ledgerline billing service: codebase map › Persistence and events] After the transaction commits, `generateInvoice` calls `publishInvoiceFinalized(invoice)` in `billing/events/publish.ts`.
u40 [Ledgerline billing service: codebase map › Persistence and events] That function publishes an `invoice.finalized` message to the `billing-events` topic.
u41 [Ledgerline billing service: codebase map › Persistence and events] The payment and email services subscribe to that topic; I did not read their code.
u42 [Ledgerline billing service: codebase map › Persistence and events] What happens when publishing fails after the commit is unknown.
u43 [Ledgerline billing service: codebase map › Persistence and events] The code logs the error and returns, so an invoice can exist without its event, but I found no job that re-sends missed events and no note saying whether one is planned.
u44 [Ledgerline billing service: codebase map › Data contract] The draft passed between the steps has this shape, defined in `billing/invoices/types.ts`:
u45 [Ledgerline billing service: codebase map › Data contract] export interface InvoiceDraft { accountId: string; period: BillingPeriod; lines: PricedLine[]; subtotalCents: number; taxCents?: number; }
u46 [Ledgerline billing service: codebase map › Data contract] `taxCents` stays undefined until `TaxClient.quote` returns.
u47 [Ledgerline billing service: codebase map › Data contract] I did not read the definitions of `BillingPeriod` and `PricedLine`.
u48 [Ledgerline billing service: codebase map › Interpretation] My reading is that `billing/pricing` acts, in effect, as the pricing boundary: as far as I could see, no code outside it reads `price_plans`, so a pricing change should only need edits there.
u49 [Ledgerline billing service: codebase map › Interpretation] This is an interpretation of the current structure, not a rule the code enforces; nothing stops another module from querying `price_plans` directly.
u50 [Ledgerline billing service: codebase map › Interpretation] In the same spirit, `generateInvoice` behaves like an orchestrator.
u51 [Ledgerline billing service: codebase map › Interpretation] It holds no pricing or tax logic of its own and only sequences the calls, which is why it reads so short for the work it starts.
u52 [Ledgerline billing service: codebase map › Open questions] What starts the regular monthly run? The admin action is clear, but I could not find the scheduler that calls `generateInvoice` for every account.
u53 [Ledgerline billing service: codebase map › Open questions] Does `priceUsage` really apply discounts? See the unconfirmed link above.
u54 [Ledgerline billing service: codebase map › Open questions] Who owns the `billing-events` topic? No owner is listed in the repository.
u55 [Ledgerline billing service: codebase map › Open questions] Why does the `invoices` table have a status column if every row is written as `finalized`? It may be reserved for drafts, but nothing in the code says so.
u56 [Ledgerline billing service: codebase map › Summary] In short, the verified invoice path is a fixed sequence inside `generateInvoice`: collect usage, price it, quote tax, write both invoice tables in one transaction, then publish `invoice.finalized`.
u57 [Ledgerline billing service: codebase map › Summary] Two parts of the map are not verified: the discounts read is only probable, and the tax provider's retry behaviour is unknown.
