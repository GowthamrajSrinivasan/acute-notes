# Ledgerline billing service: codebase map

## About this map

This note maps the invoice path of the Ledgerline billing service as of commit `a41c9e2`. I read the code by hand; nothing here was generated by a tool. Every statement says how I know it: "the code does" means I read it in the file named, "my reading" is my own interpretation, "probably" means I suspect it but did not confirm it, and "unknown" means I looked and could not find out. Refunds, dunning and the customer portal are out of scope.

## Modules on the invoice path

- `billing/invoices` holds the entry point, the draft type and the write to the invoice tables.
- `billing/usage` turns raw usage events into usage lines.
- `billing/pricing` turns usage lines into priced lines.
- `billing/tax` wraps the external tax provider.
- `billing/events` publishes billing events for other services to consume.

Each module exposes its functions through its own `index.ts` file. The modules import each other only through those index files; I found no import that reaches into another module's internal files.

## Invoice generation entry point

The code defines `generateInvoice(accountId, period)` in `billing/invoices/generate.ts`, lines 12–58. It is the only exported function in that file. The admin console's "Regenerate invoice" action calls it from `billing/admin/regenerate.ts`.

`generateInvoice` does its work in a fixed order. First, the code calls `collectUsage(accountId, period)` to get the usage lines for the period. Second, it calls `priceUsage(lines, plan)` to turn those lines into priced lines. Third, it calls `TaxClient.quote(draft)` to get the tax for the draft invoice. Finally, it writes the invoice and publishes an event, as described under "Persistence and events" below.

## Usage and pricing

The code in `billing/usage/collect.ts` defines `collectUsage(accountId, period)`. It reads the `usage_events` table, selecting the account's rows whose `occurred_at` falls inside the period, and groups them by meter into usage lines. Events flagged `is_test` are skipped. It does not write to any table.

The code in `billing/pricing/priceUsage.ts` defines `priceUsage(lines, plan)`. It reads the `price_plans` table through a helper in the same file, `loadPlan(planId)`, and multiplies each line's quantity by the plan's unit price. Prices are held as integer cents throughout, never as floating-point amounts.

`priceUsage` probably also reads the `discounts` table. The file imports a helper called `discountFor`, and the name suggests a discount lookup, but I did not find a call site and have not confirmed that it ever runs. Treat this link as unconfirmed until someone traces it.

## Tax

The code in `billing/tax/client.ts` defines a `TaxClient` class whose `quote(draft)` method sends the draft invoice to an external tax provider, Taxwell, over HTTPS. The request has a timeout of 8 seconds, set on line 21. The API key is read from the `TAXWELL_API_KEY` environment variable when the client is constructed. The response carries a tax amount for each line, which `generateInvoice` adds to the draft before saving it.

How retries work for the tax provider is not documented. `TaxClient.quote` contains no retry code, and I could not find out whether its callers retry, whether the Taxwell client library retries on its own, or what happens to the invoice when a quote times out.

## Persistence and events

The code writes the finished invoice to two tables, `invoices` and `invoice_lines`, inside one database transaction in `billing/invoices/generate.ts`, lines 44–52. If either insert fails, the transaction rolls back and neither row is kept. The `invoices` row is written with the status `finalized`; I found no code path that writes any other status.

After the transaction commits, `generateInvoice` calls `publishInvoiceFinalized(invoice)` in `billing/events/publish.ts`. That function publishes an `invoice.finalized` message to the `billing-events` topic. The payment and email services subscribe to that topic; I did not read their code.

What happens when publishing fails after the commit is unknown. The code logs the error and returns, so an invoice can exist without its event, but I found no job that re-sends missed events and no note saying whether one is planned.

## Data contract

The draft passed between the steps has this shape, defined in `billing/invoices/types.ts`:

```ts
export interface InvoiceDraft {
  accountId: string;
  period: BillingPeriod;
  lines: PricedLine[];
  subtotalCents: number;
  taxCents?: number;
}
```

`taxCents` stays undefined until `TaxClient.quote` returns. I did not read the definitions of `BillingPeriod` and `PricedLine`.

## Interpretation

My reading is that `billing/pricing` acts, in effect, as the pricing boundary: as far as I could see, no code outside it reads `price_plans`, so a pricing change should only need edits there. This is an interpretation of the current structure, not a rule the code enforces; nothing stops another module from querying `price_plans` directly.

In the same spirit, `generateInvoice` behaves like an orchestrator. It holds no pricing or tax logic of its own and only sequences the calls, which is why it reads so short for the work it starts.

## Open questions

- What starts the regular monthly run? The admin action is clear, but I could not find the scheduler that calls `generateInvoice` for every account.
- Does `priceUsage` really apply discounts? See the unconfirmed link above.
- Who owns the `billing-events` topic? No owner is listed in the repository.
- Why does the `invoices` table have a status column if every row is written as `finalized`? It may be reserved for drafts, but nothing in the code says so.

## Summary

In short, the verified invoice path is a fixed sequence inside `generateInvoice`: collect usage, price it, quote tax, write both invoice tables in one transaction, then publish `invoice.finalized`. Two parts of the map are not verified: the discounts read is only probable, and the tax provider's retry behaviour is unknown.
