# Updating notes from ChatGPT chats: the known limits, and what was done about each (2026-10-11)

Context: the chat update (AI chat → "Update from ChatGPT chats", Visualize → "Merge into existing notes", the MCP `import_content` tool) runs the merge with the decision model (Jev). `src/ai/ingest/chatUpdate.test.ts` checks it at three sizes (small 3 topics, medium 20, large 80). Four limits were listed after the first version; each is addressed below.

| # | Limit | What was done | Proof |
|---|---|---|---|
| 1 | The decision model sees only an excerpt of each topic (400 to 3,000 characters), so a contradiction of a statement deep in a long topic was missed (the new statement was filed as a fact next to the old one) | `assign.ts`: a part whose statement changes a number, version or identifier of a statement of its topic that says the same thing (most significant words shared) is asked about in round two whatever the relation answer was; the model still decides each pair. A part only a detail made suspect that the model finds no contradiction in is an ordinary part (it never hands the merge to the chat task, as a model-flagged one does). The statements are the topic's whole text, not the excerpt. | `assignConflicts.test.ts` (6 new); the medium and large scenarios put the price after the excerpt and fail without the change (0 of 2 and 0 of 3 conflicts found) |
| 2 | The tests used a deterministic stand-in for Jev, not the real model | The scenario moved to `ingest/__fixtures__/chatUpdateWorld.ts` and runs against any decision model: the stand-in (always), recorded real answers (`chatUpdateReplay.test.ts`, offline, skipped until a recording exists), and an approval-gated live capture (`contractTests/chatUpdateJev.contract.test.ts`) that records the real answers and reports what the real model found. Record and replay is itself tested (a recording answers the same scenario with the same result; a request that was not recorded is listed and fails the checks). | Not run live: needs approval. Estimated cost at Jev's price from the real request sizes: small 6 requests about $0.0003, medium 13 about $0.0016, large 38 about $0.012 (default cap $0.03, default sizes small and medium, zero retries, synthetic text only) |
| 3 | The dialog's new behaviour had no UI test | The choice of notes and mode is a function (`chooseMergeTarget`, 5 tests), the store's `mergeSourceId` is tested, and a free local end-to-end spec drives the real app: notes made by Visualize, Ask AI shows "Update from ChatGPT chats", the dialog opens on Merge with those notes and the chats panel open, a mocked share link is added and merged, the notes' text is kept once and the new passage joins its topic. | `e2e/local/chatUpdateFromAI.local.spec.ts` passes in the browser (no AI request) |
| 4 | In chat notes a user's quoted question sits at the end of the section before its answer, so new text for a topic landed below the next topic's question and a question could be filed away from its answer | Changing the layout would stop existing notes from matching new imports (every unit would differ), so `compose.ts` handles it where text is inserted: new text for a topic goes above the quoted questions that end its section, and an incoming chat's questions travel with the part that follows them. Only for notes with a ChatGPT `Source:` line; other notes are unchanged. | `compose.test.ts` (5 new) and the three scenarios assert each question sits directly with its own answer |

## Still true

- The live capture has not been run. Until it has, "works with the real Jev" is evidenced by the earlier live benchmarks (Runs 4 to 7) and by the recorded answers those produced, not by this scenario.
- Conflict detection by detail change is a heuristic for when to ask the model; it does not decide anything itself.
- The question layout is still the quoted-question-then-heading layout of the first import; only where merged text is placed changed.
